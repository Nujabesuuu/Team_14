## 0. Коротко

- **Новий функціонал MVP:** US-07 «Підтвердження гри» (правило 15 хв + 2 підтвердження, автозавершення через 3 год) і обмеження US-11 «Зіграємо ще?» (24 години, «ближче» лише з «Побаченням» в обох). Разом з US-12 це наскрізний шлях «гра → зарахування → таємна відповідь → метч», заради якого існує продукт.

## 3. Знайдені й виправлені баги

### Баг 1. До застосунку для 18+ реєструвались 13-річні (US-01, NEVER-04)

- **Як знайшли:** тест від вимог `test_minor_is_refused_and_no_account_is_created[17 years 364 days]` на старому коді: `assert (201 == 422)`. Прогалина G-01 була відома з КТ4, але код досі мав `if user.age < 13`.
- **Що цікаво:** після виправлення впали три **старі** тести (`test_profile`, `test_events`, `test_swipes`): вони реєстрували 16- і 17-річних через API, щоб перевірити «Побачення лише з 18». Тобто тести, написані колись від коду, закріпили баг як норму.
- **Як виправили:** чисте правило `app/domain/accounts.py::old_enough` (межа «рівно 18 — так, 17 р. 364 дні — ні», 29 лютого → 1 березня) і перевірка в `services/auth.py` до пошуку email, щоб неповнолітній нічого не дізнався про зайняті адреси. Старі тести тепер створюють дорослого й «омолоджують» його в базі (`set_birth_date`): друга лінія захисту («Побачення», Game Date) лишається перевіреною для акаунтів, створених до виправлення.

### Баг 2. Заблокований дізнавався про блокування (US-08, US-19, NEVER-05)

- **Як знайшли:** `test_blocked_player_cannot_join_and_learns_no_reason`: `'BLOCKED' == 'EVENT_NOT_VISIBLE'`. Контракт ще на КТ4 позначив це як ✏️, але код не змінили, а старий `test_blocks.py` очікував саме `BLOCKED`.
- **Як виправили:** `join_event` повертає той самий `403 EVENT_NOT_VISIBLE`, що й для будь-якого недоступного івенту; виправили старий тест і контракт. Мутація «повернути `BLOCKED`» тепер ловиться двома тестами.

### Баг 3. Час з SQLite без часового поясу (G-10)

- **Як знайшли:** нові правила (15 хв, 3 год, 24 год) порівнюють час з бази з `utcnow()`. SQLite повертає наївний `datetime`, і порівняння падає з `TypeError`. Той самий корінь давав видимий баг з КТ4: у JSON час без поясу, браузер читав його як місцевий, і в Києві час у чаті та на івентах був зсунутий на 2 години. Агент-тестувальник побачив час без поясу у відповідях і **обійшов** його в хелпері `parse_dt` («щоб US-07 не падав через окрему прогалину»), тобто тест маскував баг.
- **Як виправили:** тип колонки `UtcDateTime` (`models/_base.py`): при записі переводить у UTC (раніше `+02:00` зберігався як «настінний» час), при читанні додає UTC. Тепер відповіді мають `Z` (перевірено в пункті 11 чекліста).

### Баг 4. Дата «сьогодні» залежала від поясу машини (US-01)

- **Як знайшли:** тест US-01 «рівно 18 років» упав о 00:58 за Києвом і пройшов би вдень. Тест рахував день реєстрації за UTC, сервер — `date.today()`, тобто за поясом ноутбука: між 00:00 і 02:00 за Києвом та сама дата народження проходила на ноутбуці й не проходила в Docker (там UTC).
- **Як виправили:** сервер рахує вік за UTC-датою, як і денний ліміт лайків. Вимога A-03 каже «за `profiles.timezone`, за замовчуванням Київ»; для цього потрібен пакет `tzdata` на Windows, тобто нова залежність і ADR, тож це записано окремою прогалиною G-13.

### Баг 5. Івент можна було створити в минулому (US-19, G-07)

- **Як знайшли:** `test_start_time_in_the_past_is_rejected`, `test_start_time_a_minute_ago_is_rejected`: `201 == 422`.
- **Як виправили:** `domain/events.py::starts_in_past` і `422 STARTS_IN_PAST` у сервісі; час без поясу в запиті вважається UTC.

## 5. Перевірка тестів: «зламай код навмисно»

Скрипт ([6.3](../prompts/6.3_qa_audit_and_debugging.md)) по черзі псує одну умову, запускає тести, які мають це помітити, і повертає код назад.

| Правило | Мутація | Червоні тести |
|---|---|---|
| BR-01 рівно 18 | `>= ADULT_AGE` → `>` | domain «exactly 18», API «exactly 18 years» |
| NEVER-04 | перевірку віку прибрано | 3 API: 17 р. 364 дні, 16 років, «не бачить вмісту» |
| BR-11 рівно 15:00 | `>= MIN_PLAY` → `>` | 2 domain + API «15 хв обоє → зарахована» |
| BR-11 два підтвердження | `MIN_CONFIRMATIONS = 1` | 3 domain + 4 API |
| BR-10 рівно 3 год | `>= AUTO_FINISH_AFTER` → `>` | **лише** domain «exactly 3 h» |
| BR-12 рівно 24:00 | `now < closes_at` → `<=` | **лише** domain «exactly 24 h» |
| BR-13 «Побачення» в обох | `and` → `or` | 3 domain + 3 API |
| BR-13 на сервері | перевірку в сервісі прибрано (domain цілий) | 4 API |
| US-07/11 незарахована гра | перевірку `counted_at is None` прибрано | 2 API |
| BR-06 час у минулому | `starts_in_past` завжди `False` | 2 domain + 2 API |
| NEVER-05 | повернути код `BLOCKED` | 2 API |
| UI: 15 хв | `<` → `<=` у `afterGame.ts` | 1 web |
| UI: «Get closer» | `locked = false` | 1 web |
| *Після аудиту:* блок не діє на відповіді | `if target.is_banned or blocked` → `if target.is_banned` | 2 API |
| WS при автозавершенні через стрічку | `broadcast` прибрано | 1 API |
| Подвійне натискання | `ApiError(409)` → сирий `IntegrityError` | 1 API |
| Метч при одночасному «ближче» | прибрано `ON CONFLICT DO NOTHING` | 1 API |
| Підтвердження рахуються з бази | `count(*)` → `len(event.confirmations)` | спершу **вижила**; після посилення тесту — 2 API |

**Висновок:** з 18 мутацій 17 спіймано одразу. Мутація «рахувати підтвердження за списком у пам'яті» вижила: усі тести дивились на стан через наступний `GET`, а там «самолікування» зараховує гру. Проте лобі й WS будуються з відповіді на саме підтвердження, тож людина бачила б «Confirmed 2/2, waiting» до перезавантаження. Ми додали перевірку `counted_at` у відповіді на останнє підтвердження, і мутація стала червоною. Дві точні межі (рівно 3 год і рівно 24 год) ловлять лише domain-тести: в API-тесті між записом часу в базу і запитом минають мілісекунди, тож рядок «24:00» насправді перевіряє «24:00 і трохи». Тому межі з точністю до секунди живуть у чистих функціях з параметром `now`. Ще одне спостереження: мутація «прибрати перевірку на сервері, лишивши domain цілим» спіймана API-тестами, тобто правило перевіряє саме сервер, а не лише функція.

## 6. Незалежний аудит покриття (промпт 6.3)

Окремий агент з чистим контекстом прочитав вимоги, контракти, тести і зміни коду й перевірив 8 конкретних атак. Повний звіт і що ми зробили з кожною з 15 знахідок — у [prompts/6.3](../prompts/6.3_qa_audit_and_debugging.md#результат-аудиту-і-що-зробили). Кожну знахідку спершу підтвердили тестом у репозиторії, який падав, і лише потім виправили. Найважливіше:

| № | Баг | Чому 200 зелених тестів його не бачили | Як виправили |
|---|---|---|---|
| 6 | **Двоє одночасно підтверджують гру → гру не зараховано ніколи.** Кожен запит рахував підтвердження за списком у пам'яті й бачив лише своє. Повторити не можна (`ALREADY_CONFIRMED`), тож «Зіграємо ще?» для пари зникало назавжди | Усі тести підтверджували по черзі | Підтвердження рахуються з бази; рядок івенту блокується (`FOR UPDATE` на PostgreSQL); `get_event` дораховує гру, якщо щось усе ж проскочило |
| 7 | **Блокування після гри не діяло на «Зіграємо ще?».** Олена блокує Максима, а її «ближче» дає з ним метч і чат (BR-21) | Сценарію «блок після гри» немає у вимогах US-11/US-12, лише в US-08 | Заблоковані зникають з `pending`; відповідь про них не зберігається й виглядає як «метчу ще немає», бо окремий код видав би блокування (NEVER-05) |
| 8 | Одночасне взаємне «ближче» → 500 (`uq_match_pair`) | Те саме: лише послідовні запити | `INSERT … ON CONFLICT DO NOTHING`; `match.new` надсилається один раз |
| 9 | Автозавершення через стрічку не надсилало WS `event.updated`, хоча контракт це обіцяв | API-тест читав лише `GET /events/{id}` | `broadcast` після завершення в `list_events` |
| 10 | Подвійне натискання «підтвердити» → 500 | — | `409 ALREADY_CONFIRMED` |

**Що аудит перевірив і не знайшов:** хост не може зарахувати гру сам (одне підтвердження на акаунт, вийти після старту не можна); одностороння відповідь не розкривається ні в полях, ні в кодах помилок, ні по WS; час з поясом і без поясу обробляється правильно.

**Діагностика побічного ефекту.** Нові тести на одночасні запити проходили поодинці й падали в повному прогоні з `Lock … is bound to a different event loop`. Причина була в обв'язці: SQLite у пам'яті тримав одне з'єднання на весь прогін, і його `asyncio.Lock` прив'язувався до циклу подій першого тесту, якому довелось на ньому чекати. Тепер `conftest.py` робить `engine.dispose()` перед кожним тестом.

## 7. Рефлексія: де ШІ помилявся або хитрував

1. **Тест підлаштувався під баг, хоча заборона була прямо в промпті.** Агент-тестувальник побачив у відповідях час без поясу (G-10) і написав хелпер `parse_dt`, що читає такий час як UTC, «щоб US-07 не падав через окрему прогалину». Це та сама пастка, від якої застерігає завдання: тест мовчки прийняв неправильну поведінку. Ми виправили код (`UtcDateTime`), а хелпер лишили лише для формату `Z`.
2. **Старі тести, написані від коду, закріпили два баги.** Три тести реєстрували 16-річних (бо код дозволяв з 13), а `test_blocks.py` очікував код `BLOCKED`, який розкриває блокування. Обидва баги знайшли нові тести, написані від вимог, а не аудит старих.
3. **Зелений набір з 200 тестів не помітив двох блокерів.** І агент-автор коду, і агент-тестувальник перевіряли лише послідовні дії однієї людини за раз. Конкурентні запити й «блокування після гри» з'явились лише в незалежного аудитора з переліком атак. Висновок той самий, що на КТ5: тест від того самого агента, що й код, не замінює окремого погляду.
4. **Тест, що покриває вимогу, ще не означає, що він перевіряє потрібне місце.** Мутація «рахувати за списком у пам'яті» вижила, бо всі тести дивились на стан після наступного `GET`, а не на відповідь, з якої будується UI. Без мутаційної перевірки ми б цього не побачили.
5. **Межі в API-тестах слабші, ніж здаються.** Рядок «24:00 → закрито» в API-тесті насправді перевіряє «24:00 і кілька мілісекунд»: мутація `<` → `<=` його не ламає. Точні межі ловлять лише domain-тести з `now` у параметрі, тому правила з часом ми пишемо чистими функціями.
6. **Тести мигали від часу запуску.** Тест US-01 упав о 00:58 за Києвом, і за цим стояв справжній баг (баг 4). Окремо аудитор знайшов, що дати в `parametrize` рахуються під час збирання, а прогін триває 2,5 хв і може перетнути північ. Обидва місця виправлено.
7. **Цифри зі звіту агента треба перевіряти.** Тестувальник повідомив про 94 тести, а `pytest --collect-only` нарахував 92. Числа в документах беремо з команд, а не зі звітів моделі.
8. **Агент-автор коду теж помилився в процесі.** Щоб старі тести стали зеленими, він змінив `play_together` так, що той одразу зараховував гру. Через це нові тести US-07 отримали б `ALREADY_CONFIRMED`. Залишили поділ, який запропонував тестувальник: `play_together` — гра завершена, але не зарахована, `finish_and_count` — зарахована.
9. **Чого ШІ не зміг зробити.** У сесії не було браузера, тож колонку UI в ручному чеклісті (розділ 2) агент не заповнював: її пройшла людина з команди. Поки її не пройшли, позначати непройдене як пройдене ми не стали.
