# КТ4. Архітектурний дизайн і каркас проєкту: звіт і сценарій демо

> Для команди Team 14 перед практичною зустріччю. Що зроблено за кожним пунктом завдання, де це лежить, що показати за 3 хвилини і що можуть спитати на рев'ю.

## 1. Коротко: що ми зробили

Робочий прототип у нас уже був з попередніх етапів, тож на КТ4 ми не писали нових фіч, а оформили технічний дизайн і довели наявний код до вимог Walking Skeleton:

1. **Технічний аналіз вимог** ([docs/technical-analysis.md](technical-analysis.md)): 15 сутностей, 6 життєвих циклів з діаграмами станів, 24 бізнес-правила (BR-01…BR-24), 10 заборон (NEVER-01…NEVER-10), 12 технічних припущень, 8 розбіжностей між вимогами і прототипом та 4 відкриті питання з рішеннями.
2. **Архітектурні рішення** ([docs/adr/](adr/)): індекс з обмеженнями команди (4 людини, ~128 людино-годин, 0 грн, локальний запуск) і 6 нових ADR з порівнянням щонайменше трьох варіантів у кожному: структура репозиторію, UI, БД, автентифікація, формат API і помилок, приватне зберігання фото. Разом з 4 старими — 10 ADR.
3. **Технічні контракти** ([docs/contracts/](contracts/)): схема даних з типами, ключами й обмеженнями для кожної таблиці; API під кожну з 19 історій MVP зі статус-кодами; єдиний формат помилок і каталог усіх кодів; машинний `openapi.json`.
4. **Інструкції для ШІ** ([CLAUDE.md](../CLAUDE.md)): суть проєкту, стек, команди, структура папок, порядок роботи з задачею, правила кодогенерації, заборони, Definition of Done.
5. **Walking Skeleton**:
   - запуск усього однією командою `python dev.py` (Windows, macOS, Linux) або `docker compose up --build`;
   - `GET /api/v1/health` і новий `GET /api/v1/health/db`, що реально робить запит до БД;
   - єдиний формат помилок для всього API, зокрема валідації й неіснуючих маршрутів;
   - сторінка-заглушка `/status`: назва проєкту, перелік екранів з історіями, живий стан Web, API і бази даних.
6. **Промпти** ([prompts/4.1–4.4](../prompts/)): фінальна версія, перша версія і таблиця «що змінили і навіщо» для кожного кроку.

Бізнес-логіку фіч не змінювали. Усі 72 API-тести і 20 web-тестів проходять.

## 3. Підготовка до зустрічі (зробити заздалегідь)

1. **Злити гілку в `main`.** Усі зміни КТ4 лежать у гілці `docs/kt4-architecture-skeleton`. Викладач дивиться `main`, тож перед здачею відкрийте Pull Request і злийте його.
2. **Здати посилання на DistEdu** до початку зустрічі: https://github.com/Nujabesuuu/Team_14
3. **Один раз запустити `python dev.py` на ноутбуці, з якого буде демо.** Перший запуск ставить залежності (1–2 хв). Під час демо повторний запуск займає кілька секунд.
4. **Перевірити версії:** `python --version` (потрібно 3.12+), `node --version` (22+).
5. **Відкрити заздалегідь у вкладках:** `CLAUDE.md` на GitHub і [ADR-0010](adr/0010-private-photo-storage.md) або [ADR-0005](adr/0005-monorepo.md).
6. **Прогнати кроки з розділу 4** хоча б раз з таймером.

## 4. Покроковий запуск і демо (3 хвилини)

Кроки виконуються по черзі. У колонці «Де» вказано, де саме виконувати дію: у терміналі, у браузері чи в репозиторії.

| № | Де | Що зробити | Очікуваний результат |
|---|---|---|---|
| 1 | Термінал | Відкрити новий термінал і перейти в корінь репозиторію (папка `Team_14`, де лежать `dev.py`, `README.md`, `CLAUDE.md`):<br>`cd Team_14` | Термінал у корені проєкту |
| 2 | Термінал, корінь репозиторію | Запустити проєкт однією командою:<br>`python dev.py`<br>(macOS/Linux: `python3 dev.py`; альтернатива з PostgreSQL: `docker compose up --build`) | У терміналі з'являється блок `Teamate is up` з адресами. API працює на `:8000`, клієнт на `:5173` |
| 3 | Браузер | Відкрити http://localhost:8000/api/v1/health | `{"status":"ok"}` — API запущено |
| 4 | Браузер | Відкрити http://localhost:8000/api/v1/health/db | `{"status":"ok","database":"sqlite"}` — API підключився до БД і виконав запит |
| 5 | Браузер | Відкрити http://localhost:8000/api/v1/no-such-route | `{"code":"NOT_FOUND","detail":"Not Found"}` — помилки мають єдиний формат з контракту |
| 6 | Браузер | Відкрити http://localhost:5173/status | Сторінка-заглушка: назва «Teamate», три рядки Web / API / Database зі статусом `OK`, перелік екранів MVP з номерами історій |
| 7 | Браузер, сторінка `/status` | Натиснути «Check again» | Статуси оновлюються і знову показують `OK` — UI наживо звертається до API і БД |
| 8 | Браузер, сторінка `/status` | Натиснути «Open the app» | Відкривається стартовий екран застосунку (Welcome) |
| 9 | Браузер (необов'язково) | Відкрити http://localhost:8000/docs | Swagger UI з усіма ендпоінтами API |
| 10 | GitHub або редактор, корінь репозиторію | Відкрити `CLAUDE.md` | Видно розділи: проєкт, стек, команди, структура, правила кодогенерації, заборони |
| 11 | GitHub або редактор, `docs/adr/` | Відкрити `0010-private-photo-storage.md` (або `0005-monorepo.md`) і озвучити рішення | Текст для озвучення — нижче |
| 12 | Термінал з кроку 2 | Натиснути Ctrl+C | API і клієнт зупиняються |

**Що коротко пояснити під час кроків:**
- **Крок 2:** скрипт сам створює середовище, ставить залежності, наповнює БД демо-даними і запускає API та клієнт.
- **Кроки 3–5:** перевірка здоров'я API і БД, а також єдиний формат помилок `code` + `detail`.
- **Кроки 6–7:** наскрізна перевірка зв'язку трьох шарів: UI → API → БД.
- **Крок 10:** головна заборона — не вигадувати поля й ендпоінти, а брати їх з `docs/contracts`.

**Ключове архітектурне рішення (варіант 1, ADR-0010):**
«Головна обіцянка продукту — ніхто не бачить фото без згоди. Ми з'ясували, що в прототипі фото ховалось лише CSS-розмиттям, а файл лежав у публічній папці. Тому рішення: фото зберігається в приватній папці, сервер сам робить розмиті копії для кожної стадії і віддає їх лише через ендпоінт з перевіркою, на якій стадії глядач. Незнайомець отримує 404, а не 403, щоб навіть не дізнатися, що фото існує. Альтернативи — S3 з підписаними посиланнями і BLOB у БД — ми відкинули через нульовий бюджет і локальний запуск».

**Варіант 2 (простіший, ADR-0005):**
«Монорепозиторій: `apps/api` і `apps/web` поруч з документацією. Контракт API, бекенд і клієнт змінюються в одному PR, CI перевіряє обидві частини, а викладач бачить усе за одним посиланням. Nx чи Turborepo не потрібні: у нас лише два застосунки різними мовами».

**Якщо щось пішло не так під час демо:**
- порт зайнятий → закрити попередній запуск (Ctrl+C) або перезавантажити термінал;
- немає інтернету → залежності вже встановлені заздалегідь (крок 3 підготовки), `dev.py` їх не перевстановлює;
- `python` не знайдено на macOS → `python3 dev.py`.

## 5. Можливі питання на рев'ю і короткі відповіді

| Питання | Відповідь | Де показати |
|---|---|---|
| Чому FastAPI, а не Spring, якщо курс на Java? | Швидкий цикл, валідація й OpenAPI з коробки, домен тестується без БД. Досвід команди з Java базовий, а ціль — робочий продукт до кінця семестру | [ADR-0001](adr/0001-fastapi-over-spring.md) |
| Чому реляційна БД? | Інваріанти тримає сама БД: одна пара — один метч, одна відповідь на пару, не можна приєднатися двічі. SQLite — нуль налаштувань, PostgreSQL — у Docker | [ADR-0007](adr/0007-relational-db-sqlalchemy.md) |
| Чому немає міграцій? | Поки немає реальних даних, `create_all` дешевший. Alembic підключимо перед першою тестовою групою | ADR-0007, «Коли переглянути» |
| Як контракти відповідають історіям? | Кожна з 19 історій має рядок у таблиці трасування «історія → ендпоінти» | [api.md, кінець](contracts/api.md#трасування-історія--ендпоінти) |
| Що означають 🆕 і ✏️ у контрактах? | ✅ — є в коді і покрито тестами; ✏️ — ендпоінт є, але змінюється під вимоги; 🆕 — спроєктовано, реалізація на КТ5 разом з історією | [contracts/README.md](contracts/README.md) |
| Ви писали бізнес-логіку на цьому етапі? | Ні. Додали лише інфраструктуру каркаса: health/db, формат помилок, сторінку статусу, скрипт запуску. Розбіжності з вимогами зафіксували як прогалини G-01…G-08 | [technical-analysis.md, розд. 6](technical-analysis.md#6-знайдені-прогалини) |
| Як гарантуєте, що гра справді відбулась? | BR-11: ≥ 15 хв між стартом і завершенням і ≥ 2 підтвердження від різних людей; автозавершення через 3 год | technical-analysis.md, розд. 2.2 і 3 |
| Як працює авторизація? | Email + пароль (bcrypt), JWT HS256 на 7 днів у заголовку Bearer; токен у `sessionStorage`, тож дві вкладки — два акаунти для демо | [ADR-0008](adr/0008-jwt-auth.md) |
| Чи реалістично встигнути? | 128 людино-годин, з них ≤ 60 % на історії. 5 історій уже працюють повністю, 10 частково; нової роботи ≈ 64 год | [requirements.md](requirements.md#in-scope-mvp-19-історій) |
| Як ШІ допомагав і що ви перевіряли самі? | Промпти 4.1–4.4 в одній сесії; контракт звірили з кодом (OpenAPI + усі коди помилок) і знайшли 4 розбіжності; усе запущено й перевірено в браузері | [ai-log.md](ai-log.md), [4.3](../prompts/4.3_technical_contracts.md) |
