# Журнал використання ШІ

Вимога курсу: фіксувати, як саме генеративний ШІ використовувався, що з його пропозицій прийнято, що відкинуто і чому. Формат: дата · етап · що просили · результат · рішення команди.

## 2026-09-15 · КТ1 · ідея та README

- **Запит:** оцінити ідею «дейтинг для геймерів через спільну гру» як маркетолог, 1–100.
- **Результат:** 58/100. Головні ризики: монетизація «плати за фото» суперечить цінності продукту й обходиться обміном Instagram; змішування LFG і дейтингу; cold start; 18+.
- **Рішення:** прийняли критику. Переробили модель: фото розкривається поетапно за взаємною згодою, преміум продає видимість/зручність, режими Duo/Friends/Dating розділено, Dating 18+. Ідею «голосове інтро» відкинули (тімлід: не для MVP). Переоцінка: 74/100.

## 2026-09-18 · КТ3–4 · специфікація

- **Запит:** стек і архітектура під вимоги курсу (UI + backend + БД, Android надалі, React + Python).
- **Результат:** spec `docs/superpowers/specs/2026-09-18-teamate-mvp-design.md`: React + Capacitor / FastAPI / PostgreSQL-SQLite, доменні правила окремим шаром, WebSocket для реального часу.
- **Рішення:** прийнято. Альтернативи React Native і Next.js відкинуто свідомо (ADR-0002). Замість Java Spring (база команди) обрано FastAPI — ADR-0001.

## 2026-09-19 · КТ5 · реалізація

**Згенеровано ШІ і прийнято після перевірки тестами:**
- доменні модулі `events.py`, `matching.py`, `reveal.py`, `compatibility.py` та 35 юніт-тестів до них;
- REST-роутери, сервіси, схеми; 31 API-тест (httpx + in-memory SQLite);
- дизайн-система Phantom UI, усі екрани;
- seed-скрипт з 12 профілями.

**Дефекти в згенерованому коді, знайдені під час ручної перевірки в браузері (не тестами):**

| Дефект | Як знайшли | Виправлення |
|---|---|---|
| Картка в Discover і екран фідбеку залишались невидимими (`opacity: 0`) | Скриншот + `getComputedStyle` | `initial` на прямих дітях `AnimatePresence` не стартує під StrictMode у framer-motion 13. Замінено на CSS-анімацію `.deal-in`. Зафіксовано в design-system.md |
| `<button>` всередині `<button>` (Chip у картці івенту) | Попередження React у консолі | `Chip` рендерить `<span>`, якщо не має `onClick` |
| API стартував з порожньою БД | 401 при логіні з seed-акаунтом | Дефолтний шлях до SQLite залежав від `cwd`; тепер обчислюється від кореня `apps/api` |
| Форма логіну розтягувала поля на весь екран, тінь кнопки була не тієї висоти | Скриншот | `alignContent: start` для grid-форм; тінь `PhantomButton` загорнута в content-sized wrapper |
| `Conversation.match` лениво завантажувався в async-сесії → `MissingGreenlet` | Падіння API-тесту | `lazy="selectin"` |
| WebSocket-тест зависав | Таймаут pytest | Змішування event loop httpx і `TestClient` над одним in-memory SQLite; тест переписано повністю на `TestClient` |

**Відкинуті пропозиції ШІ:**
- Alembic-міграції на старті — зайве для MVP, `create_all` достатньо (зафіксовано як обмеження в architecture.md).
- Redis pub/sub для WS одразу — передчасно; описано як наступний крок (ADR-0004).
- Typing-індикатори в чаті — YAGNI.

**Що перевіряла команда самостійно:** повний демо-сценарій у двох вкладках (див. demo.md), усі 66 бекенд- і 25 фронтенд-тестів, `ruff`, `tsc`, `oxlint`, production-збірка Vite.

## 2026-09-19 · ітерація дизайну та демо-чат

- **Запит тімліда:** знайти скіл «have-taste», зробити дизайн витонченішим і менш агресивним, аватари як герої популярних ігор у стилі Persona, згенерувати зображення нейромережею, додати можливість перевірити чат без другого акаунта.
- **Скіл:** знайдено репозиторій `leonxlnx/taste-skill` (ядро `taste-skill`, `redesign-skill`, `soft-skill`), встановлено локально як скіли ШІ-асистента. Корисні правила, які лишились у проєкті: один акцент, справжні зображення замість hand-made SVG, жодних вкладених `<button>`, `prefers-reduced-motion`.
- **Авторське право:** пропозицію малювати конкретних персонажів Valorant/Dota/LoL відхилено (чужа IP). Замість них 8 архетипів (Duelist, Sage, Impostor, Builder, Pilot, Operator, Vanguard, Strategist), які читаються геймером за роллю.
- **Генерація:** `apps/api/scripts/generate_images.py` → Pollinations (безкоштовно, без ключа): 9 портретів героїв + 13 seed-фото. Перевірено вручну на якість; кілька перегенеровано зміною seed.
- **Редизайн «Velvet Arcade»** (спокійна палітра, Big Shoulders + Instrument Sans, єдина форма з одним зрізаним кутом) зроблено повністю, показано тімліду і **відкинуто**: команді ближча початкова енергія Phantom UI. Гілка `feat/redesign-v2` збережена для порівняння; повернулись до тегу `mvp-v1` і доробили його: портрети героїв замість SVG-масок, hero-картки у Welcome та онбордингу, full-bleed портрет у картці Discover.
- **Демо-чат:** бот Guide (`services/bot.py`), 3 тести (`test_bot.py`): метч після онбордингу без дублювання, відповідь у чаті, автозгода на reveal.
- **Урок для ai-log:** візуальний напрямок треба показувати на 1–2 екранах до повного переписування. Повний редизайн коштував ~1 годину і був відкинутий; ескіз коштував би 10 хвилин.

## 2026-09-21 · портрети героїв

- Портрети, згенеровані Pollinations, вийшли напівреалістичними й не збігались з референсом тімліда (плоский cel-shading, товсті контури, червоне тло). Дві спроби змінити промпт і модель стиль не дали.
- **Рішення:** нейро-портрети прибрали, повернули оригінальні SVG-маски. Тімліду передали 6 промптів для Gemini; код уже вміє підхоплювати портрет замість маски для окремих героїв (`PORTRAIT_KEYS`).

## 2026-09-27 · КТ2 · аудиторія, ціннісна пропозиція, критичний аналіз

- **Промпти.** Перші версії написав тімлід. ШІ-асистент запропонував правки: повний опис проєкту замість плейсхолдера, вибір 1 основного профілю замість 3–4 рівноправних, заборона вигадувати статистику, позначки MVP / Пізніше для функцій, незалежний запуск критика. Обидві версії і пояснення правок лежать у [`prompts/`](../prompts/).
- **Запуск.** 2.1 і 2.2 в одному чаті, 2.3 в окремому. Для цього використали окремі екземпляри LLM без доступу до коду й інструментів, щоб імітувати звичайний чат. Відповіді збережено без змін у [`docs/research/`](research/).
- **Перевірка.** Кожне технічне твердження критика звірили з кодом: 4 підтвердились, 2 частково, 1 не підтвердилось (таблиця в [README, розділ 7](../README.md#7-критичний-аналіз)).
- **Власні знахідки команди під час перевірки:**
  - оригінал «прихованого» фото можна завантажити без авторизації: ШІ лише припустив це, а ми відтворили скриптом;
  - «ближче» після гри не перевіряє вік і режим «Побачення», тож 16-річний і дорослий можуть отримати метч.
- **Розбіжність між двома відповідями ШІ.** VPC оцінила «страх відмови» як повністю закритий, а критик показав, що в Game Date на двох відсутність метчу сама видає відповідь. Висновок: одна відповідь ШІ не є істиною, перехресна перевірка різними ролями знаходить помилки.
- **Рішення тімліда:** свайпи з метчем лишаємо (з метрикою частки метчів зі свайпів); «ближче» лише між двома людьми з «Побаченням»; весь застосунок 18+; платний запит на раннє розкриття фото лишаємо з пом'якшеннями.
- **Дефект процесу.** Тест аватарів падав після попередньої ітерації: список портретів спорожнили, а тести перед комітом не перезапустили. Виправили; правило «тести перед кожним комітом» додали нижче.

## 2026-10-12 · КТ3 · вимоги, User Stories, межі MVP

- **Промпти.** Для кожного з 5 етапів спершу написали базову версію за текстом завдання, потім доопрацювали її: роль, повний контекст КТ1–КТ2, явні межі, формат відповіді, самоперевірка. Обидві версії і таблиця «що змінили і чому» лежать у [`prompts/3.1–3.5`](../prompts/).
- **Запуск.** Усі 5 промптів по черзі в одному чаті з LLM (Claude Sonnet 5.5), без доступу до коду: модель не знала про прототип і різала скоуп лише за ресурсом команди. Відповіді збережено без змін у [`docs/research/`](research/). Відповіді перевірили за критеріями завдання, їхньої якості вистачило, тому на сильнішу модель не перемикались.
- **Уточнення посеред ланцюжка.** У відповіді 3.4 модель сама позначила 4 відкриті питання (відлік 24 годин, межі 4-ї стадії фото, блокування в уже призначеному івенті, ліміт свайпів). Відповіді команди додали на початок промпту 3.5, щоб критерії не розійшлися з рішеннями.
- **Що змінила команда:**
  - повернули в MVP вибір маски (US-18) і створення івенту (US-19): обидві вже працюють у прототипі й важливі для персон;
  - прийняли відкладення «Моїх тіммейтів» і нагадувань, хоча на КТ2 планували їх у MVP;
  - ухвалили 8 рішень за пропозиціями QA від ШІ (автозавершення через 3 години, блокування в обидва боки, маска за замовчуванням тощо);
  - виправили історію US-16, де було два «щоб»;
  - для кожної історії звірили стан прототипу. Виявилось, що свайпи показують незнайомцям розмите фото, хоча за критеріями має бути лише маска. Це ще один прояв проблеми з КТ2 «фото приховане лише на екрані».
- **Урок.** Модель без знання про прототип оцінила MVP у 74–75 годин «з нуля» і відрізала дві функції, які вже працюють. Сліпий запуск корисний, бо дає чесну межу, але звіряти з реальним станом коду має команда.

## 2026-10-27 · КТ4 · архітектурний дизайн і каркас

- **Інструмент.** Claude Code (Claude Opus 5.5) у репозиторії; запускав Ярослав Шах (BA/QA). Чотири промпти 4.1–4.4 в одній сесії по черзі. На відміну від КТ3, модель **бачила код**: прототип уже існує, і сліпий аналіз знову відрізав би те, що працює.
- **Результат:** [технічний аналіз вимог](technical-analysis.md), ADR 0005–0010 та [індекс з обмеженнями команди](adr/README.md), [контракти](contracts/) (схема даних, API, каталог помилок, `openapi.json`), [CLAUDE.md](../CLAUDE.md), каркас: `dev.py`, `GET /api/v1/health/db`, єдиний формат помилок, сторінка `/status`.
- **Що змінено в коді (лише інфраструктура, без бізнес-логіки):**
  - `GET /api/v1/health/db` виконує `SELECT 1`, при збої повертає `503 DB_UNAVAILABLE`;
  - валідація, неіснуючий маршрут і непередбачений збій тепер теж повертають `{code, detail}`. Раніше FastAPI віддавав `{"detail": [...]}`, і клієнт мав окрему гілку розбору;
  - публічна сторінка `/status` у клієнті: назва, перелік екранів з історіями, живий стан API і БД;
  - `dev.py` запускає все однією командою на Windows, macOS і Linux, бо команди README з `.venv/bin/` на Windows не працювали, а Docker є не в усіх.
- **Перевірка людиною і скриптами:** 72 API-тести (3 нові), 20 web-тестів (2 нові), `ruff`, `tsc`, `oxlint`; `python dev.py` з нуля; кожну URL-адресу з README перевірено `curl` і в браузері.
- **Розбіжності, які знайшли, звіряючи чернетку контракту з кодом** (експорт OpenAPI + grep усіх `ApiError`): `GET /events/{id}` не повертає `EVENT_NOT_VISIBLE`; заблокований при `join` отримує `403 BLOCKED`, тобто дізнається про блокування всупереч US-08 (позначено ✏️); `leave` повертає `NOT_PARTICIPANT` зі статусом 409, а не 403; `POST /blocks` не має `USER_NOT_FOUND`.
- **Свідомо не зроблено:** 8 прогалин між вимогами КТ3 і прототипом (поріг віку 13, публічні фото, немає підтвердження гри тощо) лише зафіксовано в [technical-analysis.md, розділ 6](technical-analysis.md#6-знайдені-прогалини) і в контрактах з позначкою 🆕/✏️. Бізнес-логіку на КТ4 не змінюємо, це робота КТ5.
- **Урок.** Модель з доступом до коду швидко пише контракт «як є», але тоді він мовчки фіксує баги прототипу як норму. Правило «вимоги важливіші за код» і позначки ✅/✏️/🆕 розділяють, що є, що зміниться і що нове.

## Правила роботи з ШІ в команді

1. Кожен PR з ШІ-кодом має тести на доменні правила, які він реалізує.
2. Ніякого коду, який автор не може пояснити на рев'ю.
3. Чутливі дані (реальні email, паролі, токени) у промпти не потрапляють — лише seed-дані.
4. Візуальні зміни перевіряються в браузері, не тільки тестами: типові ШІ-дефекти (анімації, вкладеність DOM) тести не ловлять.
5. Перед кожним комітом запускаються всі тести, навіть якщо зміна «лише в даних».
6. Твердження ШІ про код і безпеку перевіряються в самому коді або скриптом, перш ніж потрапити в документи.
