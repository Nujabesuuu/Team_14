# Архітектурні рішення (ADR)

> **КТ4, крок 2.** Кожен ADR фіксує одне рішення: контекст, порівняння варіантів, рішення, наслідки і момент, коли його треба переглянути.
> Промпт: [prompts/4.2_adr_generation.md](../../prompts/4.2_adr_generation.md). Вхідні дані: [технічний аналіз вимог](../technical-analysis.md).

## Обмеження команди, під які ухвалено рішення

| Обмеження | Значення | Що з цього випливає |
|---|---|---|
| Склад | 4 людини: тімлід і full-stack, backend, DevOps, BA/QA | Один стек на всю команду, мінімум рухомих частин |
| Час | ~4 год на тиждень на людину, ~8 тижнів до фінального демо ≈ 128 людино-годин, з них ≤ 60 % на історії | Беремо інструменти, де валідація, документація API і тести є «з коробки» |
| Запуск | Локально на ноутбуці, демо в браузері на двох вкладках, надалі Android APK | Жодних хмарних сервісів як обов'язкової залежності; запуск 1 командою |
| Бюджет | 0 грн | Лише open source і безкоштовні інструменти; без платних БД, хостингу, push-сервісів |
| Досвід | Базова Java з курсу; тімлід пише на React і Python; усі працюють з ШІ-асистентами | Стек, у якому ШІ генерує передбачуваний код і де команда може його пояснити на рев'ю |
| Продукт | Реальний час (чат, метч), суворі правила згоди й віку, мобільний клієнт | Чисті доменні правила окремим шаром, WebSocket, мобільна збірка з того самого коду |

## Шаблон

```markdown
# ADR-NNNN: Назва рішення

**Статус:** запропоновано | прийнято | замінено ADR-XXXX · дата

## Контекст        — яка проблема і які обмеження команди на неї впливають
## Варіанти         — таблиця порівняння за однаковими критеріями
## Рішення          — що обрали, одним-двома реченнями
## Наслідки         — що стає простіше, що складніше, які ризики приймаємо
## Коли переглянути — конкретна умова, за якої рішення перестає бути правильним
```
