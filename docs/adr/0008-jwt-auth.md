# ADR-0008: Автентифікація email + пароль, JWT Bearer на 7 днів

**Статус:** прийнято · 2026-10-27

## Контекст

Потрібно знати, хто робить запит, для REST і для WebSocket. Демо відбувається на одному ноутбуці у двох вкладках, які мають бути двома різними акаунтами. Бюджет нульовий, а сторонні провайдери входу (Google, Discord) потребують реєстрації застосунку і публічного redirect URL. Вимога US-01 — перевірка віку 18+ під час реєстрації, тож дату народження ми збираємо самі.

## Варіанти

| Критерій | **Власний JWT (HS256)** | Серверні сесії + cookie | OAuth (Google / Discord) | Firebase Auth / Auth0 |
|---|---|---|---|---|
| Працює для WebSocket | Так, `?token=` | Так, cookie, але складніше в Capacitor | Через свій токен після OAuth | Через SDK |
| Дві вкладки = два акаунти | Так, токен у `sessionStorage` | Ні, cookie спільна для вкладок | Ні | Ні |
| Інфраструктура | Немає | Сховище сесій | Реєстрація застосунку, redirect URL | Акаунт у сервісі |
| Бюджет | 0 | 0 | 0 | Безкоштовний тариф |
| Відкликання токена | Ні до закінчення строку | Так | Залежить | Так |
| Перевірка віку | У нашій реєстрації | У нашій реєстрації | Окремий крок після входу | Окремий крок |

## Рішення

- `POST /auth/register` і `POST /auth/login` повертають `access_token` (JWT HS256, `sub` = id користувача, `exp` = 7 днів).
- Пароль зберігається лише як bcrypt-хеш; email приводиться до нижнього регістру.
- Клієнт надсилає `Authorization: Bearer <token>`; WebSocket підключається з `?token=` і закривається з кодом `4401` при невалідному токені.
- Токен зберігається в `sessionStorage` (свідомо для демо: дві вкладки = два акаунти).
- Секрет — змінна `JWT_SECRET`; значення за замовчуванням лише для розробки.
- Роль модератора (US-10) — поле `users.role`, яке сервер перевірятиме в залежності `require_moderator`. Окремої системи прав немає. Поле і залежність додаються разом з US-10.

## Наслідки

- Без refresh-токена: через 7 днів треба увійти знову. Для MVP прийнятно.
- Токен не можна відкликати. Тому акаунт, заблокований модератором (US-10), відсікатиметься перевіркою `banned_at` у `get_current_user` на кожному запиті, а не відкликанням токена.
- Токен у `sessionStorage` вразливий до XSS. Пом'якшення: React екранує вивід, ми не використовуємо `dangerouslySetInnerHTML`.

## Коли переглянути

Перед публічним запуском: refresh-токени, httpOnly-cookie для веба, вхід через Discord (основна платформа аудиторії), обмеження частоти спроб входу.
