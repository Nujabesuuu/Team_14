# Тестова стратегія Teamate

> **КТ6.** Що, чим і де ми перевіряємо в нашому проєкті. Документ про Teamate, а не про тестування взагалі.
> Промпт, з яким його складали: [prompts/6.1_testing_strategy.md](../prompts/6.1_testing_strategy.md). Звіт про результат: [testing-report.md](testing-report.md).

## 1. Що для нас ризиковано

Продукт обіцяє безпечне знайомство, тож найдорожча помилка не «кнопка з'їхала», а порушене правило: неповнолітній у застосунку, фото, видне незнайомцю, одностороннє «ближче», яке хтось побачив, метч без згоди. Тому автотести стоять передусім на **бізнес-правилах з числами** (BR-01…BR-24) і **заборонах** (NEVER-01…NEVER-10) з [technical-analysis.md](technical-analysis.md), а не на верстці.

Друге джерело ризику — **час**: 15 хвилин гри, 3 години до автозавершення, 24 години на відповідь, «сьогодні» за часовим поясом. Ці межі перевіряємо з точністю до хвилини, а то й секунди.

## 2. Рівні тестів під наш стек

| Рівень | Інструмент | Що перевіряє | Чого не робить |
|---|---|---|---|
| **Domain (unit)** | pytest, без БД | Чисті функції з `app/domain/`: машина станів івенту, правило зарахування гри, вікно 24 год, «ближче» лише з «Побаченням», метч, стадії фото, модерація. Граничні значення: 17 р. 364 дні / 18; 14:59 / 15:00; 23:59 / 24:00 | Не торкається HTTP і бази |
| **API (інтеграційні)** | pytest + httpx `ASGITransport` + справжня SQLite у пам'яті | Сценарії Given-When-Then через публічний REST: права доступу, коди помилок з [errors.md](contracts/errors.md), наслідки дії (стан після, а не лише відповідь), приватність (`PublicUser` без email, дати народження, автора скарги) | Не мокає сервіси й базу. Не запускає справжній сервер і мережу |
| **Web (компонентні)** | Vitest + Testing Library + jsdom | Стани екранів і сторів: обов'язкові поля, розгалуження за `code` помилки, що бачить людина після відповіді сервера, WS-події | Мокаємо **лише** `fetch` на межі клієнта. Не перевіряємо вигляд: CSS у jsdom не рахується |
| **Ручний smoke** | Браузер, дві вкладки, [чекліст](testing-report.md#2-ручний-smoke-чекліст) | Верстка Phantom UI, анімації і `prefers-reduced-motion`, живі оновлення між двома акаунтами, реальний час у потрібному поясі | Не повторює те, що вже ловлять автотести |

**Чого свідомо немає:** E2E у браузері (Playwright, Cypress) — це нова залежність і браузери в CI, а за правилами команди нова інфраструктура потребує ADR; навантажувальних тестів (один процес, A-05); тестів Android-оболонки Capacitor.

## 3. Межі (Scope)

**Автотестами покриваємо:**

- кожне правило BR-xx — тест у `tests/domain/` (якщо правило чисте) або `tests/api/` (якщо потрібні права чи база);
- кожну заборону NEVER-xx — щонайменше один негативний API-тест: людина пробує й отримує відмову з правильним `code`;
- сценарії історій у роботі з таблиць Examples — по рядку на тест;
- контракт помилок: кожен новий `code` з'являється хоча б в одному тесті.

**На ручну перевірку залишаємо:**

- вигляд і верстку (зрізані кути, шрифти, кольори, темна тема), анімації й `prefers-reduced-motion`;
- живу взаємодію двох людей у двох вкладках (WebSocket між справжніми браузерами);
- відображення часу в місцевому поясі (у jsdom пояс завжди один);
- Android: вибір фото з галереї, кнопка «назад», клавіатура над полем чату;
- тексти інтерфейсу і зрозумілість повідомлень про помилки.

## 4. Організація файлів

| Що | Де | Назва |
|---|---|---|
| Чисті правила | `apps/api/tests/domain/` | `test_<правило>.py`: `test_game_rules.py`, `test_feedback_rules.py` |
| API за історією | `apps/api/tests/api/` | `test_usXX_<коротко>.py`, коли файл написано від критеріїв однієї історії (`test_us07_confirm_game.py`); `test_<ресурс>.py` для старіших тестів за ресурсом |
| Обв'язка | `apps/api/tests/conftest.py`, `tests/helpers.py` | Фікстури `client`, `make_user`; хелпери `seed_games`, `onboard`, `play_together`, `finish_and_count`, `set_event_times` |
| Web | `apps/web/src/test/` | `<фіча>.test.tsx` |

**Як називаємо тест:** назва читається як сценарій (`test_game_of_14_59_is_not_counted`), у docstring — ID історії і назва сценарію з [requirements.md](requirements.md). Рядки таблиці Examples — `pytest.mark.parametrize` з `ids`, що повторюють рядок.

**Як пишемо перевірку:** завжди і статус, і `code` (`assert r.status_code == 409 and r.json()["code"] == "FEEDBACK_WINDOW_CLOSED"`). Після дії дивимось стан окремим запитом (`GET /matches` порожній), а не лише відповідь на дію.

## 5. Тестові дані та ізоляція

- **Окрема база на кожен тест.** `conftest.py` ставить `DATABASE_URL=sqlite+aiosqlite://` до імпорту застосунку, а autouse-фікстура `_fresh_schema` перед **кожним** тестом відкриває нове з'єднання (`engine.dispose()`) і робить `drop_all` + `create_all`. Тести не залежать від порядку і не бачать даних один одного. Демо-база `teamate.db` і seed тестами не використовуються взагалі.
- **Люди створюються через публічний API** (`make_user` → `POST /auth/register`), тож тест проходить ту саму валідацію, що й справжній користувач. Прямо в базу пишемо лише те, чого API свідомо не дає: роль модератора (`make_moderator`) і моменти в часі (`set_event_times`).
- **Час не мокаємо.** Чисті функції приймають `now` параметром. В API-тестах «гра тривала 14:59» чи «минуло 24 год 1 хв» задаємо, переписуючи `started_at`, `finished_at`, `counted_at` у базі, а сервер порівнює їх зі справжнім поточним часом. Тому тест не залежить від того, коли його запустили.
- **Фото** пишуться в `./.test-media`, а не в `media/`.
- **WebSocket-хаб** живе в пам'яті процесу; тести, що відкривають сокет, закривають його в межах тесту.
- **Web:** перед кожним тестом `vi.restoreAllMocks()` і скидання сторів Zustand (`useAuth.setState(...)`), `fetch` підмінюється `vi.stubGlobal` лише в межах тесту.

## 6. Як ми пишемо тести з ШІ

1. **Від вимог, а не від коду.** Агент, який генерує тести, отримує [requirements.md](requirements.md), контракти й тестову обв'язку, але **не читає `app/`**. Якщо код поводиться інакше, ніж каже вимога, тест падає, і це знахідка, а не привід переписати очікування.
2. **Спершу червоний.** Новий тест запускаємо на старому коді. Тест, який одразу зелений для ще не реалізованої поведінки, — підозрілий.
3. **«Зламай код навмисно».** Для ключових правил тимчасово псуємо умову (`>=` → `>`, `15` → `14`, прибираємо перевірку) і переконуємось, що відповідний тест червоніє. Результати — у [testing-report.md](testing-report.md#5-перевірка-тестів-зламай-код-навмисно).
4. **Незалежний аудит.** Покриття перевіряє інший агент з чистим контекстом ([6.3](../prompts/6.3_qa_audit_and_debugging.md)): що з вимог не покрито, які assert-и слабкі, де мок замінює перевірку.

## 7. Запуск

```bash
python test.py            # усе: ruff, pytest, tsc, oxlint, vitest
python test.py --api      # лише бекенд
python test.py --web      # лише клієнт
```

Ті самі кроки виконує CI ([.github/workflows/ci.yml](../.github/workflows/ci.yml)) на кожен push у `main` і на кожен PR. Тест, що падає, не вимикаємо і не позначаємо `skip`: шукаємо причину.
