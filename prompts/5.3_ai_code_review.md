# 5.3 Код-рев'ю за допомогою ШІ

**Мета:** перед злиттям у `main` отримати незалежну перевірку змін епіка «Скарга → рішення модератора»: відповідність архітектурі, безпека, обробка помилок, чистота коду.

**Як запускали:** локальний ШІ-агент для аудиту `git diff`, окремий від того, що писав код.

- Автор коду: Claude Code, модель Claude Fable 5.2 ([5.1](5.1_code_generation.md)).
- Рев'юер: окремий субагент Claude Code на іншій моделі (Claude Sonnet 5.5) з чистим контекстом. Він не бачив ні переписки, ні міркувань автора: лише репозиторій, diff гілки і промпт нижче. Рев'юеру заборонено змінювати файли.
- Чому так: модель, яка щойно написала код, схильна підтверджувати власні рішення. Інша модель без історії діалогу читає код так, як його читатиме тіммейт.
- Звіт рев'юера без змін опубліковано коментарем у [PR #2](https://github.com/Nujabesuuu/Team_14/pull/2), під ним — відповідь, що виправлено і що свідомо відхилено.

## Промпт рев'юера

```text
Ти — senior-розробник, який робить код-рев'ю Pull Request перед злиттям у main. Код писав інший
ШІ-агент; твоя задача — знайти те, що він пропустив, а не похвалити. Файли НЕ змінюй і нічого
не коміть: ти лише читаєш код, запускаєш перевірки і пишеш звіт.

Контекст:
- Репозиторій Teamate (знайомства геймерів через спільну гру). Правила проєкту: CLAUDE.md.
- PR реалізує епік «Скарга → рішення модератора»: історії US-09 і US-10 з docs/requirements.md
  (чеклисти і сценарії Given-When-Then), правила BR-23, BR-24 і заборона NEVER-06
  з docs/technical-analysis.md, контракт у docs/contracts/ (api.md, data-schema.md, errors.md).
- Зміни: git diff main...HEAD. Читай не лише diff, а й код довкола: викликачів, сусідні сервіси,
  тести. Помилки найчастіше живуть на стику нового коду зі старим.

Перевір по черзі й у звіті дай розділ на кожен пункт:

1. Відповідність вимогам. Для кожного пункту чеклистів US-09 і US-10 і кожного сценарію:
   реалізовано / частково / ні, і яким тестом це доведено. Назви сценарії без тесту.

2. Архітектура (CLAUDE.md): правило продукту — чиста функція в app/domain; доступ до БД і права —
   app/services; роутери тонкі; клієнт ходить лише через api/client.ts; UI лише з примітивів
   design-system і токенів. Чи збігаються код, docs/contracts і openapi.json? Чи немає полів,
   ендпоінтів або кодів помилок, яких немає в контракті?

3. Безпека. Спробуй зламати:
   - авторизація: чи може не модератор прочитати чергу, ухвалити рішення, дізнатись, які скарги існують;
   - витік автора скарги (NEVER-06): будь-яка відповідь REST чи подія WebSocket, яку отримує
     не модератор;
   - перебір: чи відрізняється відповідь для існуючого і неіснуючого акаунта, івенту, розмови;
   - заблокований акаунт: вхід, уже виданий токен на КОЖНОМУ ендпоінті, WebSocket, нова реєстрація;
     чи є шлях, яким заблокований лишається видимим або активним;
   - зловживання: спам скаргами, скарга на людину, з якою не перетинався, гонка двох рішень,
     ескалація ролі через API;
   - ін'єкції та XSS: коментар скарги показується модератору — як він рендериться;
   - приватність: що саме бачить модератор і чи не більше, ніж потрібно для рішення.

4. Обробка помилок. Сервер: лише ApiError з кодами з errors.md, правильні HTTP-статуси, транзакції
   (чи може рішення зберегтись без блокування або навпаки), що буде при збої після commit.
   Клієнт: чи показується помилка людині, чи не лишається «вічний спінер», що відбувається
   при 403 ACCOUNT_BANNED посеред сесії і при втраті мережі.

5. Чистота коду: дублювання, мертвий код, незрозумілі назви, коментарі, що пояснюють «що», а не
   «чому», зайва складність, порушення стилю сусіднього коду.

6. Тести: чи перевіряють вони поведінку, а не реалізацію; чи є граничні значення (коментар 500/501);
   який важливий випадок не покрито; чи є тест, який пройде, навіть якщо зламати правило, яке він
   нібито перевіряє.

Запусти перевірки сам і вкажи фактичний результат (не довіряй опису PR):
  apps/api: .venv/bin/ruff check app tests && .venv/bin/ruff format --check app tests && .venv/bin/pytest -q
  apps/web: npm run typecheck && npm run lint && npm test && npm run build

Формат звіту (markdown, українською, назви файлів і коду — як є):
- «Вердикт»: можна зливати / можна після виправлення блокерів / не можна, одним абзацом.
- «Результат перевірок»: що запускав і що отримав.
- Таблиця зауважень: № | Серйозність (блокер / суттєве / дрібне) | Файл:рядок | Що не так і як це
  відтворити | Що пропонуєш. Блокер — діра в безпеці, втрата даних, порушення вимоги або контракту.
  Не більше 15 зауважень, найважливіші першими. Не пиши про те, що вже ловить ruff, tsc чи oxlint.
- «Що зроблено добре»: 3–5 пунктів, лише конкретика.
- «Чого я не перевіряв»: чесно, що лишилось поза рев'ю.

Кожне зауваження має бути перевіреним: відкрий файл і процитуй рядок. Якщо не впевнений — так і
напиши («гіпотеза»), а не видавай за факт. Якщо зауважень рівня «блокер» немає, не вигадуй їх.
```

## Що змінили порівняно з першою версією і чому

| Було | Стало | Навіщо |
|---|---|---|
| «Зроби рев'ю diff» | Роль, контекст вимог і контракту, шість розділів перевірки | Без вимог рев'юер оцінює лише стиль. З вимогами він може сказати «сценарій X не покрито» |
| Рев'ю тією самою сесією, що писала код | Окремий агент на іншій моделі з чистим контекстом | Автор не бачить власних сліпих зон. Це той самий принцип, що в незалежного критика на КТ2 |
| «Перевір безпеку» | Конкретні атаки: перебір id, витік автора скарги, живий токен заблокованого, гонка рішень | Загальне «перевір безпеку» дає загальні поради («додайте rate limiting»). Список атак дає відтворювані знахідки |
| — | «Запусти перевірки сам, не довіряй опису PR» | Опис PR теж писав ШІ. Рев'юер має мати власні факти |
| — | Серйозність, файл:рядок, спосіб відтворення, ліміт 15 | Звіт на 60 дрібниць ніхто не розбирає. Ліміт і серйозність змушують ранжувати |
| — | «Позначай гіпотези», «не вигадуй блокери», «чого не перевіряв» | Рев'юер-ШІ теж галюцинує. Кожне зауваження ми перевіряємо в коді, перш ніж виправляти (правило 6 з ai-log) |
| — | Заборона змінювати файли | Рев'ю і виправлення розділені: видно, що знайшов рев'юер і що з цим зробив автор |
