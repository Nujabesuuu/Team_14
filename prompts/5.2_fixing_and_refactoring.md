# 5.2 Виправлення помилок і рефакторинг

**Мета:** довести згенерований код до стану, коли лінтер, перевірка типів, тести і збірка проходять без зауважень, а код узгоджений з базою даних і контрактом.

**Як працювали:** у тій самій сесії Claude Code, що й [5.1](5.1_code_generation.md). Агент сам запускає перевірки після кожного кроку, тому окремих ручних запитів «виправ цю помилку» майже не було: діяло одне правило циклу виправлень (нижче). Для випадків, коли помилку приносить людина з терміналу або з CI, команда користується шаблоном з останнього розділу.

**Детерміновані перевірки (ті самі, що в CI):**

```bash
# apps/api
.venv/bin/ruff check app tests && .venv/bin/ruff format --check app tests && .venv/bin/pytest -q
# apps/web
npm run typecheck && npm run lint && npm test && npm run build
```

---

## Правило циклу виправлень

```text
Після кожного логічного кроку запускай усі перевірки для застосунку, який змінював.
Якщо щось червоне:
1. Прочитай повідомлення повністю і назви причину одним реченням, перш ніж щось міняти.
2. Виправляй причину, а не симптом. Заборонено: вимикати правило лінтера, ставити # noqa чи
   @ts-ignore без пояснення, послаблювати або пропускати тест, міняти очікування тесту під код.
3. Якщо падає тест, спершу виріши, хто правий: тест (вимога) чи код. Вимоги важливіші.
4. Після виправлення запусти ВСІ перевірки знову, а не лише ту, що падала.
5. Якщо те саме падає втретє, зупинись і поясни мені, що не сходиться.
Форматування (ruff format) застосовуй автоматично, це не рішення.
```

## Що реально спрацювало

### 1. `ruff check`: довгі рядки в нових тестах

```text
E501 Line too long (122 > 120)
   --> tests/api/test_reports.py:255:121
E501 Line too long (122 > 120)
   --> tests/api/test_reports.py:279:121
Found 5 errors.
```

Причина: довгі `assert` з вкладеними викликами. Виправлено `ruff format` (перенесення рядків), логіка тестів не змінювалась. Після цього `All checks passed!`, 94 тести.

### 2. Рефакторинг: перевірка ролі перед пошуком скарги

Перша версія доменного правила:

```python
def can_decide(is_moderator: bool, current: ReportStatus) -> str | None:
    if not is_moderator:
        return "MODERATOR_ONLY"
    ...
```

Щоб викликати її, сервіс спершу шукав скаргу за id. Тоді гравець без ролі отримував `404` на неіснуючу скаргу і `403` на існуючу, тобто міг перебирати id. Запит на рефакторинг:

```text
У services/reports.py роль модератора має перевірятись ДО будь-якого звернення до скарги,
і в черзі, і в рішенні. Розділи: require_moderator(user) у сервісі (як require_premium),
а в domain лиши can_decide(current) лише про стан скарги. Онови доменний тест.
Додай API-тест: гравець отримує 403 MODERATOR_ONLY незалежно від того, чи існує id.
```

### 3. Узгодження з базою: стара локальна база після зміни схеми

У проєкті немає міграцій ([ADR-0007](../docs/adr/0007-relational-db-sqlalchemy.md)): `create_all` створює нові таблиці, але не додає колонки в наявні. Після появи `users.role` і `users.banned_at` API зі старим файлом `teamate.db` стартував би без помилок і впав би вже на першому запиті з `no such column: users.role`. Щоб не лишати цю пастку тіммейтам, дали запит:

```text
Стара локальна база після зміни моделей має давати зрозумілу помилку на старті, а не падати
посеред запиту. Не додавай Alembic і не пиши власних міграцій (ADR-0007). Порівняй колонки
моделей з фактичними колонками в БД після create_all; якщо чогось бракує, зупини старт
з повідомленням, що саме відсутнє і якою командою пересоздати базу. dev.py має не чекати
30 секунд, якщо процес API вже завершився.
```

Результат на старій базі:

```text
RuntimeError: The database is older than the code (missing: users.role, users.banned_at).
Recreate it: `python dev.py --fresh`, or `docker compose down -v` for the Docker setup.
```

### 4. Одночасне рішення двох модераторів

Якщо перевірка «скарга ще нова» і запис рішення — два окремі кроки, то два модератори, які натиснули одночасно, обидва пройдуть перевірку, і друге рішення мовчки перезапише перше. Тому до сервісу одразу була вимога:

```text
Зроби запис рішення атомарним: UPDATE reports ... WHERE id = :id AND status = 'new'.
Якщо оновлено 0 рядків — REPORT_ALREADY_DECIDED. Наслідки блокування виконуй лише тоді,
коли саме цей запит записав рішення.
```

### 5. `ruff` на `dev.py` (поза CI)

`dev.py` не входить у перевірки CI, але агент прогнав лінтер і по ньому: `E501` у рядку з прапорцем `--fresh` (виправлено переносом) і `UP036 Version block is outdated`. Друге зауваження свідомо **не** виправляли: перевірка `sys.version_info < (3, 12)` потрібна саме для того, щоб на старому Python людина побачила зрозуміле повідомлення, а не помилку синтаксису. Це приклад, коли зауваження лінтера відхиляється з поясненням, а не вимикається мовчки.

## Шаблон запиту, коли помилку приносить людина

```text
Ось вивід <команда> з гілки <гілка>:

<повний вивід терміналу або лог CI, без скорочень>

1. Поясни причину одним-двома реченнями і покажи рядок, де вона виникає.
2. Запропонуй найменше виправлення. Не чіпай код, якого помилка не стосується.
3. Якщо для виправлення треба змінити контракт у docs/contracts або тест, скажи про це окремо
   і поясни, чому правий код, а не контракт чи тест.
4. Після виправлення запусти всі перевірки з CLAUDE.md і покажи підсумковий рядок кожної.
```

## Що змінили порівняно з першою версією і чому

| Було | Стало | Навіщо |
|---|---|---|
| «Виправ помилки лінтера і тестів» | Правило з 5 кроків: причина → виправлення причини → усі перевірки знову | Без «назви причину» агент підганяє код, поки не позеленіє, і часто міняє тест замість коду |
| — | Явний перелік заборонених «виправлень» (`# noqa`, `@ts-ignore`, пропуск тесту) | Найшвидший спосіб зробити CI зеленим — вимкнути перевірку. Саме це й треба заборонити |
| — | «Хто правий: тест чи код» | Тест написаний зі сценарію вимог. Якщо він падає, найчастіше не так зроблено код |
| — | Ліміт трьох спроб | Нескінченний цикл «виправив → зламав інше» дешевше перервати й розібрати з людиною |
