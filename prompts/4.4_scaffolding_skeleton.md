# 4.4 Каркас проєкту (Walking Skeleton) і інструкції для ШІ

**Мета:** отримати живий наскрізний каркас UI → API → БД, що запускається однією командою, і файл правил для ШІ-асистента в корені репозиторію. Бізнес-логіку фіч не писати.

**Як запускали:** у тій самій сесії Claude Code після [4.3](4.3_technical_contracts.md). Особливість нашої команди: робочий прототип уже є (`apps/`), тож задача була не згенерувати порожній каркас з нуля, а **довести наявний код до вимог Walking Skeleton** і нічого не зламати в логіці.

**Результат:** [CLAUDE.md](../CLAUDE.md), [dev.py](../dev.py), `GET /api/v1/health/db`, обробники помилок у `apps/api/app/core/errors.py`, сторінка `/status` (`apps/web/src/pages/Status.tsx`), оновлений [README](../README.md#швидкий-старт).

## Фінальна версія промпту

```text
Роль: ти tech lead, який готує репозиторій до роботи команди з ШІ-асистентами. На цьому етапі ЗАБОРОНЕНО писати чи змінювати бізнес-логіку фіч (apps/api/app/domain, services, наявні екрани). Можна лише інфраструктуру каркаса.

Контекст:
- Монорепозиторій (ADR-0005): apps/api — FastAPI + SQLAlchemy (SQLite / PostgreSQL), apps/web — React 19 + Vite. Прототип з 25+ ендпоінтами вже працює, 69 API-тестів і 18 web-тестів зелені.
- Контракти: docs/contracts/ (data-schema, api, errors). Рішення: docs/adr/.
- Демо на практичній зустрічі: запуск з чистого терміналу 1–2 командами, відповідь /api/health, відкритий UI-заглушка, показ файлу правил для ШІ.

Завдання:
1. Аудит каркаса. Для кожного шару (UI, API, дані) перевір, чи виконано вимоги Walking Skeleton:
   - API стартує і має ендпоінт перевірки здоров'я;
   - UI відкривається в браузері і показує назву проєкту й перелік майбутніх екранів;
   - БД підключається, і це можна ПОКАЗАТИ (тестове з'єднання або застосована схема);
   - проєкт запускається 1–2 командами на Windows, macOS і Linux, зокрема без Docker.
   Для кожного пункту: виконано / ні / частково і що саме бракує.
2. Закрий лише прогалини з аудиту мінімальними змінами:
   - ендпоінт перевірки БД, що реально виконує запит, з помилкою 503 у форматі контракту;
   - єдиний формат помилок для валідації, неіснуючого маршруту і непередбаченого збою (ADR-0009), сумісний з наявним api/client.ts;
   - публічна сторінка-заглушка, що показує назву, перелік екранів з історіями і живий стан API та БД (наскрізна перевірка UI → API → БД);
   - скрипт запуску однією командою лише на стандартній бібліотеці Python: створює venv, ставить залежності, наповнює демо-даними, запускає API і клієнт, зупиняє обидва по Ctrl+C.
   До кожної зміни — тест. Наявні тести не змінювати, крім тесту health, який розширюється.
3. Створи CLAUDE.md у корені: суть проєкту, стек, команди збірки/запуску/тестів (з поправкою для Windows), структура папок з призначенням кожної, порядок роботи з задачею (історія → правила → контракт → домен → сервіс → клієнт → тести), правила кодогенерації саме цього коду (ApiError, lazy="selectin", PublicUser, design-system), заборони, Definition of Done.
4. Онови README: запуск 1 командою з Docker і без нього, як перевірити каркас (health, health/db, /status), де лежать документи КТ4.

Правила:
- Наслідуй стиль сусіднього коду: назви, коментарі, структура, мова інтерфейсу (англійська).
- Після змін прогони: ruff check, ruff format --check, pytest, tsc, oxlint, vitest. Запусти скрипт і перевір кожну URL-адресу curl і в браузері.
- Заборони в CLAUDE.md мають бути конкретними для цього репозиторію, з посиланням на документ, а не загальними порадами.

Формат відповіді: таблиця аудиту, перелік змінених файлів з поясненням «навіщо», результати перевірок.
```

## Що змінили порівняно з першою версією і чому

| Було | Стало | Навіщо |
|---|---|---|
| «Згенеруй структуру проєкту з нуля» | «Доведи наявний код до вимог Walking Skeleton» + аудит | Генерація з нуля затерла б робочий прототип. Аудит показав, що бракує лише трьох речей: перевірки БД, єдиного формату помилок і запуску без Docker однією командою |
| — | Явна заборона чіпати `domain/`, `services/`, наявні екрани | Вимога КТ4 «не пишемо бізнес-логіку». Після 4.1 модель знає про прогалини (поріг віку 13 замість 18 тощо) і без заборони почала б їх виправляти, ламаючи наявні тести |
| «Додай health-check» | Перевірка БД, що виконує `SELECT 1`, з 503 у форматі контракту | Простий `{"status":"ok"}` не доводить, що БД підключена, а це окремий пункт завдання |
| — | Скрипт лише на стандартній бібліотеці Python, для Windows теж | Docker встановлено не в усіх (на ноутбуці, де готували КТ4, його немає), а команди README з `.venv/bin/` на Windows не працюють |
| «Створи CLAUDE.md» | Перелік розділів + «заборони конкретні для цього репозиторію з посиланням на документ» | Без цього файл виходить загальним («пиши чистий код»). Корисні заборони — ті, що посилаються на контракти, ADR і правила безпеки |
| — | «До кожної зміни — тест; прогони всі перевірки; перевір у браузері» | Правило з ai-log: тести перед кожним комітом, візуальні зміни — в браузері |
