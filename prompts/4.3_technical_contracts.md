# 4.3 Технічні контракти: схема даних, API, формат помилок

**Мета:** спроєктувати контракти, під які пишеться код: таблиці з типами й обмеженнями, ендпоінти під кожну історію MVP зі статус-кодами і єдиний формат помилок.

**Як запускали:** у тій самій сесії Claude Code після [4.2](4.2_adr_generation.md). Модель мала технічний аналіз, ADR і код прототипу (моделі, схеми Pydantic, роутери). Після відповіді контракти звірили з кодом: експорт OpenAPI, grep усіх `ApiError` у сервісах.

**Результат:** [docs/contracts/](../docs/contracts/) — `data-schema.md`, `api.md`, `errors.md`, `openapi.json`.

## Фінальна версія промпту

```text
Роль: ти backend-архітектор, який пише контракти для команди з 4 людей. Контракт — це домовленість, за якою клієнт і сервер пишуть різні люди з різними ШІ-асистентами, тож у ньому не має бути нічого «на здогад».

Вхідні дані:
- docs/requirements.md — 19 історій MVP і сценарії Given-When-Then.
- docs/technical-analysis.md — сутності, стани, правила BR-01…BR-24, заборони NEVER-01…NEVER-10, прогалини G-01…G-08.
- docs/adr/ — особливо ADR-0007 (БД), ADR-0008 (JWT), ADR-0009 (REST і формат помилок), ADR-0010 (приватні фото).
- Код: apps/api/app/models/ (таблиці), schemas/ (Pydantic), routers/ (ендпоінти), core/errors.py (ApiError).

Завдання:
1. Схема даних (data-schema.md):
   - загальні правила: тип PK, час, enum, JSON-поля, каскади, як створюється схема;
   - Mermaid erDiagram;
   - для КОЖНОЇ таблиці: поле | тип | обмеження (PK, FK з ON DELETE, UQ, IX, NN) | значення за замовчуванням | опис;
   - складені ключі й унікальні обмеження, які тримають бізнес-правила (одна пара — один метч тощо);
   - нові таблиці й поля, потрібні для історій, яких ще немає в коді (підтвердження гри, скарги, роль модератора), познач 🆕;
   - таблиця «історія → таблиці → обмеження».
2. API (api.md):
   - домовленості: базовий шлях, автентифікація, формат часу й id, коди успіху;
   - спільні об'єкти (PublicUser, Event, Match) у вигляді JSON;
   - ендпоінти, згруповані за кроками шляху користувача й історіями: метод | шлях | тіло запиту з обмеженнями | успіх (код + тіло) | помилки (статус + code);
   - службові ендпоінти Walking Skeleton: GET /health і GET /health/db;
   - протокол WebSocket: повідомлення клієнта й сервера;
   - таблиця трасування «історія → ендпоінти».
3. Помилки (errors.md):
   - формат {code, detail} і поле fields для валідації;
   - значення кожного HTTP-статусу і що робить клієнт;
   - каталог усіх кодів, згрупований за доменом, з історією-джерелом.

Правила:
- Те, що вже є в коді, опиши ТОЧНО як є (назви полів, коди, статуси) і познач ✅. Не «покращуй» мовчки.
- Те, що треба змінити, щоб відповідати вимогам, познач ✏️ і поясни, що саме змінюється.
- Нове — 🆕. Не вигадуй ендпоінтів, яких не потребує жодна історія MVP.
- Помилки безпеки не розкривають причину (заблокований бачить «недоступно», чуже фото — 404).

Самоперевірка: кожна US-01…US-19 має щонайменше один ендпоінт у трасуванні; кожен code з каталогу трапляється в api.md; кожне 🆕 поле в API має місце в схемі даних.

Формат: три markdown-файли українською; назви полів, шляхів і кодів — як у коді.
```

## Що змінили порівняно з першою версією і чому

| Було | Стало | Навіщо |
|---|---|---|
| «Опиши API» | Ендпоінти згруповано за кроками шляху й історіями + таблиця трасування | Критерій оцінювання — відповідність контрактів історіям MVP. Перелік за ресурсами (`/events`, `/matches`) цього не показує |
| — | Позначки ✅ / ✏️ / 🆕 і правило «наявне описуй точно як є» | Якщо модель «причеше» коди помилок, контракт перестане збігатися з кодом, і клієнт, написаний за контрактом, зламається на першому ж запиті |
| «Додай формат помилок» | Окремий файл з формою, значенням статусів і повним каталогом | Без каталогу кожен розробник вигадує свій `code`, і клієнт не може на них покластися |
| — | Службові `/health` і `/health/db` у контракті | Потрібні для Walking Skeleton і демо; без них перевірка БД лишалась неявною (`create_all` на старті) |
| — | «Помилки безпеки не розкривають причину» | Код на кшталт `403 BLOCKED_BY_USER` виглядає логічно, але прямо порушує US-08: заблокований не має дізнатися про блокування |
| — | Самоперевірка трасування | US-15 (підказка) природно реалізується полем `opener_hint`, а не ендпоінтом, тож її легко загубити в трасуванні |

**Що перевірила команда після відповіді:** експорт `openapi.json` з запущеного API; grep усіх `ApiError(...)` у сервісах. У чернетці контракту знайшли й виправили 4 розбіжності з кодом: `GET /events/{id}` не повертає `EVENT_NOT_VISIBLE`; заблокований при `join` зараз отримує `403 BLOCKED`, а не `EVENT_NOT_VISIBLE` (позначено ✏️); `leave` повертає `NOT_PARTICIPANT` зі статусом 409, а не 403; `POST /blocks` не має `USER_NOT_FOUND`.
