# 6.2 Генерація автотестів від вимог

**Мета:** автотести для ключових історій, написані від критеріїв приймання (Given-When-Then), а не від коду, щоб тест не закріпив наявний баг як норму.

**Історії:** US-01 (реєстрація 18+), US-19 (створення івенту), US-07 (підтвердження гри), US-11 + US-12 («Зіграємо ще?» і метч). US-07 і US-11 — новий функціонал КТ6, US-01 і US-19 вже були в коді, але з відомими прогалинами G-01 і G-07.

**Як запускали:** Claude Code (Claude Opus 5.5), 2026-11-25. Тести писав **окремий субагент в ізольованому git worktree** з кодом `main` до змін КТ6. Головний агент паралельно реалізовував US-07 і US-11 в основній копії. Так виконувалось одразу три умови:

- агент-тестувальник **не бачив `app/`** (заборона в промпті; виняток — імена класів моделей для імпорту);
- тести запускались на **старому** коді, тож видно, що вони справді червоні там, де поведінки ще немає або вона неправильна;
- інтерфейс чистих функцій (`game_counts`, `feedback_open`, `closer_allowed`…) зафіксовано в промпті **до** коду, як контракт, і його реалізували вже під ці тести.

**Результат:** 92 тести в 6 файлах (53 API + 39 domain за `pytest --collect-only`; агент у звіті нарахував 94 — рахував вручну) ([звіт, розділ 1](../docs/testing-report.md#1-що-покрито-автотестами)). На старому коді: 59 червоних, 1 файл не збирався (немає модуля `app/domain/feedback.py`), решта зелені. Наявні тести агент не змінював.

## Як керувати часом в API-тестах

Годинник у застосунку не підмінюємо. Час гри задаємо прямо в базі через `SessionLocal` і модель `Event`
(поля started_at, finished_at, counted_at з data-schema.md) — так само, як helpers.make_moderator пише роль.
Пиши SQL через `sqlalchemy.update(Event)`, а не setattr, щоб відсутня колонка дала помилку, а не тихий пропуск.
Додай такі хелпери в tests/helpers.py (не ламаючи наявні):
- set_event_times(event_id, *, started_at=None, finished_at=None, counted_at=None)
- finish_and_count(client, host_h, guest_h, game) — зіграти, підтвердити обома, зробити гру ≥ 15 хв і зарахованою;

## Що покрити

Для кожної історії: успішний шлях (Happy Path) + граничні значення + помилки й заборонені дії.
Граничні значення беремо точно з вимог: 17 років 364 дні / рівно 18; 14:59 / 15:00 хв; 1 / 2 підтвердження;
3 год від старту; 23:59 / 24:00 / 24:01 від зарахування; місць 1 / 2 / 10 / 11; час початку в минулому.

1. US-01 (tests/api/test_us01_registration.py): Scenario Outline віку (25, рівно 18, 17р364д, 16) через POST /auth/register;
   неповнолітній після відмови не має акаунта (вхід тими самими даними → 401) і не бачить стрічки (без токена → 401);
   повторний вхід → GET /me повертає той самий профіль; у відповіді немає birth_date і password_hash, де їх не має бути.
2. US-19 (tests/api/test_us19_create_event.py): створення → хост перший учасник і is_host; інший гравець бачить івент у стрічці;
   місця 2/10 ок, 1/11 → 422 VALIDATION_ERROR; назва 2/3/80/81 символ; час у минулому → 422 STARTS_IN_PAST;
   заблокований хостом не бачить івенту в стрічці.
3. US-07 (tests/api/test_us07_confirm_game.py + tests/domain/test_game_rules.py): POST /events/{id}/confirm за контрактом;
   таблиця з Scenario Outline (15 хв обоє → зарахована; 45 хв обоє → так; 14:59 обоє → ні; 10 хв → ні; 45 хв лише один → ні);
   незарахована гра не відкриває «Зіграємо ще?» (409 GAME_NOT_COUNTED); стороння людина → 403 NOT_PARTICIPANT;
   до завершення → 409 EVENT_NOT_FINISHED; повторне підтвердження → 409 ALREADY_CONFIRMED;
   автозавершення через 3 год без дії хоста (GET івенту показує finished і finished_at = started_at + 3 год), після чого можна підтвердити.
4. US-11 + US-12 (tests/api/test_us11_us12_play_again.py + tests/domain/test_feedback_rules.py):
   «ближче» залежить від «Побачення» в обох — 4 рядки таблиці (closer_allowed у GET і 422 CLOSER_REQUIRES_DATING у POST);
   вікно 23:59 → можна, 24:01 → 409 FEEDBACK_WINDOW_CLOSED; feedback_closes_at = counted_at + 24 год;
   комбінації відповідей: closer+closer → метч і чат, closer+again і closer+no → немає;
   Максим вимкнув «Побачення» після «ближче» Олени → closer йому недоступний, метчу немає;
   одностороння відповідь невидима: у Максима немає метчу, GET /matches порожній, а відповідь Олени не потрапляє в жодне поле його GET feedback.
   Для «Побачення» в профілі використай PUT /me з modes, що містить "dating" (див. contracts/api.md, US-03).

## Правила якості

- Один тест = один сценарій або один рядок таблиці (pytest.mark.parametrize з ids, що читаються як рядок Examples).
- У docstring або назві тесту — ID історії і назва сценарію з requirements.md.
- Кожен assert перевіряє і статус, і `code` помилки. Не пиши `assert r.status_code in (400, 422)`.
- Жодних моків сервісів чи БД: лише публічний API через фікстуру client і реальна SQLite у пам'яті.
- Після дії перевіряй наслідок (стан через GET), а не лише відповідь на саму дію.
- Не дублюй наявні тести: спершу подивись tests/api/*.
